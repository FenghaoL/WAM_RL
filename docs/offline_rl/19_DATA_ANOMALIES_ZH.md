# 数据异常与处理记录

此文件集中记录需要向用户明确说明的异常、证据和处理；不能只在代码里过滤后继续。新的数据冲突应补充证据并在对话里单独指出。最新实验方案见 [18 重建与 episode recipe](18_REBUILD_AND_EPISODE_RECIPE_ZH.md)。

| 发现 | 证据 | 对已有结果的影响 | 当前处理 |
|---|---|---|---|
| 250 处 tick 跳号 | 相邻保存帧之间全部匹配暂停/接管/恢复事件；配置 `pause_frames_stored=false` | 旧 history 被多次错误重置，跨越暂停的转移被过滤 | 按用户确认保持 episode 连续；旧 cache 不复用，新建全部转移与 cache |
| 12 个 `dropped_tick=True` 的保存行 | 各行前后 tick 仍逐一递增 | 旧代码把跨这些保存行的窗口过滤掉 | 保留该字段供审计；不把它单独当作缺失帧或 episode 边界 |
| 9 条 manifest 成功却没有成功帧 | 用户确认录像只到半插入，采集提前停止，最终成功未录到 | 旧基线排除了 9 条，不能用末帧伪造 +1，也不能当作失败终止 | 本次全部进入训练；4 条仅用前半段；观察奖励 0，结尾保留 bootstrap，recipe 明确标 censored |
| 旧验证集没有失败 | 原 `_val` 目录 4 条：3 个标注成功、1 个提前结束录像 | 旧验证误差不代表失败表现 | 固定留出 `183057/ep0` 和 `225809/ep1`；原 `_val/ep0` 按用户要求移入训练；split 不再从目录名推断 |
| 成功标注可出现在 HOLD，且是当前画面首次成功 | 用户明确标注语义；早期检查已有多例 | 若把成功绑定当前动作，会发生奖励时间错位 | 按已确认规则归因上一条动作；HOLD 内成功前移到该 HOLD 的第一张画面 |
| 旧主 cache 目录已不存在 | 2026-10-26 检查 `cylinder103_skip_hold/cache` 不存在 | 无法继续依赖旧 cache 做训练/重算 | 新路径从头导出；剩余旧 probe/concurrency cache 也已清理，清理清单在新运行目录 `old_cache_cleanup.json` |
| 准备脚本首次使用 stride=2，而旧实验为 1 | CPU 准备后对比 config/窗口数发现，不涉及已运行模型 | 若直接启动会额外改变训练窗口密度，影响对照 | GPU 导出前已纠正为 1，并删除该次未使用的准备产物重新生成；正式数据为 19,730 转移、stride=1 |
| 同步部署历史时钟与原始 cache 时钟不同 | 部署客户端每 8 动作请求一张观察，没有原始每 tick 图像/暂停信息 | 旧在线 smoke 只证明给定帧序列的计算一致，不能证明闭环时间轴完全相同 | 既有部署文档保留此限制；本轮只重建离线数据，不声称已解决在线采样对齐 |

原始 tick、墙钟间隔、parquet 身份和标注身份继续保留，不为“看起来连续”而改写原始证据。暂停两端可能存在关节跟踪收敛或相机画面变化；用户确认的连续任务语义不等于像素/关节数值逐项相等。
