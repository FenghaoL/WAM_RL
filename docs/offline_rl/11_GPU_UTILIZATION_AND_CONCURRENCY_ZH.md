# 缓存导出 GPU 利用率、ETA 与临时双副本测试

日期：2026-10-25，America/Detroit。用户决定保持原四卡任务速度，双副本只做隔离测试，完成后退出，不更改正式导出的调度、模型精度或缓存语义。

## 1. 当前负载与 ETA

最初查询时，四张 A100 40GB 每卡占19,260MiB，计算利用率约39–44%；12秒连续采样也存在等待间隙。显存占用与计算利用率不同：前者很大一部分是常驻模型参数，填满显存不自动缩短运行时间。

当地00:23附近，已完成19,120 / 43,680观察，43.8%。按每个rank实际帧数和均速，最长剩余约62分钟，预计01:25左右完成缓存。该时间不包含之后的两个500步RL pilot；数据解码、写盘、临时竞争和各episode历史长度会使估算变化。

当前正式导出每卡一个模型，推理batch=1，8个原始观察共用一个planner anchor，按当前帧产生OVCR KV与10步去噪参考动作。RL训练的batch64与此处冻结WAM导出batch无关。

短序列、多个Python调用、CPU视频处理与同步/拷贝都可能产生GPU空隙；本轮没有逐算子profile，因此不能把所有空闲归因于某一个阶段。

## 2. 为什么可以试双副本，但不能先假设一定更快

按约18–19GiB/副本的实测，有机会在40GB卡上容纳两个batch1副本；余量较少，不能由半显存推出可任意提高并发。增加副本可能填补等待间隙，也可能只增加计算/显存带宽竞争。

[NVIDIA官方优化说明](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/optimization.html)将batching和多个model instance列为两种吞吐优化，并明确收益依赖具体模型，需要测量。该文档的示例数字不能套用于本WAM，也不意味着本轮使用了Triton。

真正的batch推理通常比重复模型更节省参数显存，但当前部署包装器还有单样本返回、状态与历史管理，不能只修改一个batch-size参数就当作已支持批量导出。改造时还需验证因果历史、offset、参考动作与缓存结果一致。

## 3. 测试约束与产物

只在GPU0增加一个临时副本，设置allocator上限为总显存47%，导出320观察到独立目录，包含从无历史到最多6帧历史的情形。原worker PID、正式cache文件、checkpoint、BF16和去噪步数均保持不变。测试期间GPU0短暂共享算力；额外进程完成后释放显存。

- `runs/offline_rl/cylinder103_skip_hold/concurrency_probe.log`：额外副本的加载、逐段耗时和显存。
- `concurrency_probe/`：独立的320观察缓存和完成信息，不合并进正式cache。
- `concurrency_measurement.json`：两进程均进入推理之后，原GPU0 worker与临时worker在同一时间窗口内的计数变化；用于比较**合计吞吐**，不能只看某个worker变慢多少。
- `status_20261025.json`：测试前的四卡进度与ETA快照。

结果以本文件后续测量记录为准。单卡试验不是所有GPU、整个数据集的严格同段A/B；模型加载时间与正式任务中的数据复杂度也需单独考虑。


## 4. 已取得的稳定窗口测量

两副本均进入推理后的90.10秒窗口，原worker完成160观察，临时worker完成160观察，合计 **3.55观察/秒**。原单副本GPU0的平均约1.73观察/秒，因此本次短测接近2倍合计吞吐。两进程各自约1.78观察/秒；不是把某个worker的延迟缩短一半。

GPU0的nvidia-smi采样为38,262MiB（37.37GiB），计算利用率85–99%；其他GPU仍保持原单副本。临时模型加载耗时307.75秒，未计入上述吞吐窗口。预留余量有限，当前结论只支持本配置可放两个副本，不支持三副本或任意增大batch。

这是90秒计数窗口，日志计数每16观察更新，存在量化误差；两副本此时处理的episode和历史长度也不同。只能视为可行性与吞吐证据，不能承诺全目录始终精确2倍。用户已明确保持原调度，因此不将该优化部署到正式任务。
