# 为什么 int4 更慢，为什么 MiniMax-H3 比 Wan2.2 慢 200 倍

这份文档回答三个问题，从零开始解释，不假设你了解 GPU 或量化：

1. 为什么 int4 明明更省显存，却比 int8 慢 4.3 倍？
2. 为什么 MiniMax-H3 和 AHA-WAM 显存差不多，推理时间却是 1 秒 vs 232 秒？
3. 这是不是说明 MiniMax 这类模型本质上没法嵌进 WAM？
4. **改造 MiniMax 到底值不值得？**（第 4 节，直接结论：不值得，且给了替代方案）

所有数字都是在这台机器（A100-SXM4-40GB）上实测或按本仓库的配置算出来的。

---

## 第 0 节：先建立三个概念

后面所有解释都建立在这三个概念上。如果只想看结论，可以跳到第 1、2、3 节的"结论"。

### 概念 1：token —— 模型眼里的"最小单位"

模型不是直接看像素的。一段视频进模型之前要经过两次压缩：

```
原始视频  13 帧 x 384 x 320 像素
   │
   │  ① VAE 编码器：空间压 16 倍，时间压 4 倍
   ▼
latent    4 帧 x 24 x 20 x 48 通道
   │
   │  ② patchify：每 2x2 个 latent 格子打包成 1 个 token
   ▼
token     4 x 12 x 10 = 480 个 token
```

**480 就是 AHA-WAM 每次前向要处理的 token 数。**
Transformer 的工作量几乎正比于 token 数，所以这个数字非常关键。

同样算法算 MiniMax-H3（576x480 画布，124 帧）：

```
124 帧 x 576 x 480
  → VAE（空间 16 倍、时间 4 倍）→ 31 帧 x 36 x 30
  → patchify 2x2                → 31 x 18 x 15 = 8370 个 token
```

**8370 vs 480，差 17.4 倍。** 记住这个数。

### 概念 2：FLOPs —— 要做多少次乘加

神经网络里绝大部分计算是矩阵乘法。一个 `[M, K] × [K, N]` 的矩阵乘需要

```
FLOPs = 2 × M × K × N
```

（`2` 是因为每个输出元素都要做一次乘法和一次加法。）

对一个 Transformer，把所有层的矩阵乘加起来，有个非常好用的近似：

```
一次前向的 FLOPs ≈ 2 × 参数量 × token 数
```

这个公式解释了本文的一切。注意它里面**没有分辨率、没有帧数**——
那些都已经被折进"token 数"了。

扩散模型还要乘上**去噪步数**，因为每一步都是一次完整的前向：

```
生成一个视频的 FLOPs ≈ 2 × 参数量 × token 数 × 去噪步数
```

### 概念 3：roofline —— GPU 有两种"堵车"方式

GPU 干活分两件事：**从显存里读权重**，和**用这些权重做乘加**。
两件事同时进行，所以总时间由慢的那一件决定。A100 的两个上限是：

| 能力 | A100-40GB 的上限 |
| --- | --- |
| 算力（bf16 张量核） | 312 TFLOP/s（每秒 312 万亿次乘加） |
| 显存带宽（HBM2e） | 约 1.5～2 TB/s |

关键在于：**权重只需要读一次，但可以用在很多个 token 上。**
一个 `[K, N]` 的权重矩阵占 `2·K·N` 字节（bf16），
拿它处理 M 个 token 要做 `2·M·K·N` 次运算。所以

```
算术强度 = 计算量 / 读取字节数 = (2·M·K·N) / (2·K·N) = M
```

**算术强度就等于 token 数 M。** 于是分界线是：

```
临界 M = 算力上限 / 带宽上限 = 312e12 / 2e12 ≈ 156
```

| 情况 | 名字 | 谁是瓶颈 |
| --- | --- | --- |
| M < 156 | **内存带宽瓶颈** (memory-bound) | 忙着搬权重，算力闲着 |
| M > 156 | **算力瓶颈** (compute-bound) | 权重早就读进来了，忙着算 |

典型的 memory-bound 场景是**大语言模型一个字一个字往外蹦**（M=1）：
为了生成一个 token，要把整个模型的权重从显存里过一遍，算力利用率不到 1%。

而我们这两个视频模型：

| 模型 | token 数 M | 落在哪一侧 |
| --- | --- | --- |
| AHA-WAM 视频分支 | 480 | **算力瓶颈**（480 > 156） |
| MiniMax-H3 | 8370 | **算力瓶颈**（远超 156） |

**两个都是算力瓶颈。** 这一句话就是第 1 节的答案。

## 第 1 节：为什么 int4 反而更慢

### 1.1 "weight-only 量化"到底做了什么

我们用的是 **weight-only quantization（只量化权重）**：

- **权重**（模型学到的参数，固定不变）→ 存成 int8（1 字节）或 int4（半字节）
- **激活值**（数据流过网络时的中间结果）→ 仍然是 bf16（2 字节）

问题来了：int4 的权重和 bf16 的激活值**没法直接相乘**，硬件里没有这种指令。
所以真正执行的时候是：

```
从显存读 int4 权重（省了 4 倍带宽）
   ↓
解包 + 反量化回 bf16          ← 额外开销，纯粹是多出来的活
   ↓
做 bf16 矩阵乘                ← 算力消耗和不量化时一模一样
```

**关键：数学运算量一点没变，只是搬运的字节数少了。**

### 1.2 于是结论就很显然了

| | memory-bound (M 小) | compute-bound (M 大) |
| --- | --- | --- |
| 省下来的 | 4 倍带宽 —— 而带宽正是瓶颈 | 4 倍带宽 —— 但带宽根本不是瓶颈 |
| 多出来的 | 反量化开销（相对小） | 反量化开销（纯亏） |
| 净效果 | **快** | **慢** |

int4 是为大语言模型一个字一个字解码那种场景发明的。
视频 DiT 是彻底的 compute-bound，用 int4 只会亏。

这不是我的推测，是公认结论：
[Nunchaku/SVDQuant 的 diffusers 博客](https://huggingface.co/blog/nunchaku-diffusers)明确写
"DiT 推理即使 batch=1 也是 compute-bound，所以 weight-only 量化没有实测加速"；
[为什么 int4 weight-only 不能加速 prefill](https://dev.to/ji_ai/why-int4-weight-only-quantization-doesnt-speed-up-prefill-1b45)
用 roofline 讲了同一件事。

### 1.3 A100 上还有一层额外的坑

torchao 的 int4 在 A100 (sm_80) 上**只有一个内核能用**：
`tile_packed_to_4d`，也就是 tinygemm 的 `aten::_weight_int4pack_mm`
（`plain` 和 `preshuffled` 要 mslk 库，`plain_int32` 没有 CUDA 实现，
我三个都试过，只有这个能跑）。

而 tinygemm **是专门为 M≈1 手写的内核**。
[PyTorch 官方博客](https://pytorch.org/blog/accelerating-llm-inference/)的原话是：
int4 weight-only 在 batch size 1 时 tinygemm 性能最好，
但随着 batch 增大效率下降——他们因此引入 GemLite 来补大 batch 的场景。

int8 就没这个问题：大 M 时它反量化完直接把活交给 **cuBLAS**（NVIDIA 高度优化的通用矩阵乘库），
所以能跑满硬件。

### 1.4 实测

我在这台 A100 上直接量了（`bf16 / int8 / int4` 三种，同一个矩阵乘）：

| 矩阵形状 (M × K × N) | bf16 | int8 | int4 | int4 相对 bf16 |
| --- | --- | --- | --- | --- |
| LLM 解码 `1 × 5376 × 14336` | 0.136 ms | 0.583 ms | **0.085 ms** | **1.59x 快** |
| 小 batch `8 × 5376 × 14336` | 0.142 ms | 0.589 ms | 0.138 ms | 1.03x |
| AHA-WAM FFN `480 × 3072 × 14336` | 0.303 ms | 0.595 ms | 2.946 ms | **0.10x（慢 10 倍）** |
| MiniMax FFN `8370 × 5376 × 14336` | 4.977 ms | 5.739 ms | 84.785 ms | **0.06x（慢 17 倍）** |

换成吞吐量看更直观（A100 bf16 峰值 312 TFLOP/s）：

| 矩阵形状 | bf16 | int8 | int4 |
| --- | --- | --- | --- |
| `1 × 5376 × 14336` | 1.2 | 0.3 | 2.0 |
| `480 × 3072 × 14336` | 139.7 | 71.2 | 14.4 |
| `8370 × 5376 × 14336` | **221.7** | **224.4** | **15.2** |

三个现象一目了然：

1. **int4 恒定在 ~15 TFLOP/s，完全不随 M 增长。** 这就是"给 M=1 写的内核"的指纹——
   它压根没打算利用大 batch 的并行度。
2. **int8 在大 M 时追平 bf16**（224.4 vs 221.7 TFLOP/s），因为反量化的成本被摊薄了，
   实际算力由 cuBLAS 提供。所以 int8 在这里几乎是"白送的显存节省"。
3. **只有在 M=1 那一行 int4 才赢**（1.59x）。那正是它被设计出来的场景。

### 1.5 那为什么端到端只慢 4.3 倍，不是 17 倍？

因为一次生成里不止有矩阵乘：注意力的 softmax、LayerNorm、
VAE 编解码、以及组件在 CPU/GPU 之间搬运——这些都没被量化，
把 GEMM 那 17 倍的劣势稀释成了整体 4.3 倍（988 s vs 232 s）。

### 1.6 结论 + 正确的做法

> **int4 慢是因为视频模型是算力瓶颈，而 weight-only 量化只优化带宽、还额外增加反量化开销；
> 再叠加 A100 上唯一可用的 int4 内核是为 batch=1 写的，两个因素叠在一起就是 17 倍。**

如果目标是"又省显存又快"，正确的路子是 **W4A4**——权重和激活**都**量化成 4 bit，
让矩阵乘本身用低精度硬件指令跑。代表工作是 SVDQuant / Nunchaku。
但那需要专门的内核和校准流程，而且同样要看硬件支不支持，
本次没有做（A100 上的支持也有限）。

**给你的实际建议：**

| 你想要 | 用什么 |
| --- | --- |
| 快 | `QUANT=int8` |
| 省显存 | `QUANT=int4 --memory-reserve-margin 20GB` |
| 两者都要 | 目前在 A100 上没有现成方案 |

## 第 2 节：为什么 MiniMax-H3 比 AHA-WAM 慢 200 倍

### 2.1 先解开"显存差不多"这个误会

显存和速度**衡量的是完全不同的东西**：

```
显存占用 ≈ 参数量 × 每个参数几字节        ← 和"要算多少"无关
计算量   ≈ 参数量 × token 数 × 去噪步数    ← 和"存多少"无关
```

量化只动了第一个式子的"每个参数几字节"：33B 参数从 bf16 的 2 字节压到 int4 的 0.5 字节，
于是 61.7 GiB → 19.46 GiB，正好和 5B 模型 bf16 的 9.31 GiB 落到同一个量级。

**但第二个式子里的"参数量"还是 33B，一个都没少。** 量化不会让模型变小，
只是让每个数字占的空间变小。所以显存追平了，计算量完全没追平。

### 2.2 计算量差多少：把三个因子拆开

用第 0 节的公式，我按两个模型的真实配置算了一遍：

| | AHA-WAM VideoDiT | MiniMax-H3 transformer |
| --- | --- | --- |
| 参数量 | 5.00 B | 33.12 B（**6.6x**） |
| 层数 | 30 | 50 |
| hidden / ffn | 3072 / 14336 | 5376 / 14336 |
| token 数 | 480 | 8370（**17.4x**） |
| 去噪步数 | 20 | 31（**1.6x**） |
| 每步线性层 FLOPs | 3.6 TFLOP | 258.0 TFLOP |
| 每步注意力 FLOPs | 0.2 TFLOP（占 5.5%） | 100.4 TFLOP（占 **28%**） |
| **一次生成总计** | **76.7 TFLOP** | **11,112 TFLOP** |

**145 倍。** 实测墙钟时间是 232 s / 1.2 s = 193 倍，剩下的 48 倍差额来自
VAE 解码（124 帧要过一个 36 层的 transformer 解码器）、
Qwen3-VL 33B 编一次文本、以及组件在 CPU/GPU 之间通过 PCIe 换页。

### 2.3 重要澄清：Wan2.2 本身**一点也不小**

看到"AHA-WAM 13 帧 / MiniMax 124 帧"很容易得出一个错误结论：
"哦，Wan 是个小模型，MiniMax 是个大模型"。**不是这样。**

`Wan2.2-TI2V-5B` 官方发布的用法是 **720P、24 fps、5 秒**，
也就是 **121 帧 1280x704** —— 和 MiniMax-H3 的 124 帧几乎一模一样。
[官方 model card](https://huggingface.co/Wan-AI/Wan2.2-TI2V-5B) 里写的是
"在单张消费级显卡上 9 分钟内生成一个 5 秒 720P 视频"。**9 分钟**，不是 1.2 秒。

把两个模型都按各自的原生设置算一遍：

| 配置 | 帧数 | latent 帧 | token | 步数 | FLOPs | 估算耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| **Wan2.2-TI2V-5B 原生** 1280x704 | 121 | 31 | **27,280** | 50 | **24,015 TFLOP** | ~428 s |
| **MiniMax-H3 原生** 1344x768 | 124 | 31 | **31,248** | 49 | **115,794 TFLOP** | ~2062 s |
| Wan2.2 在 **AHA-WAM 里的用法** 384x320 | 13 | 4 | **480** | 20 | **74 TFLOP** | ~1.3 s |
| MiniMax-H3 **我们跑的** 576x480 | 124 | 31 | 8,370 | 31 | 11,112 TFLOP | ~198 s |

（估算耗时按 A100 实测的 18% MFU 折算。428 s ≈ 7 分钟，和官方说的"9 分钟"对得上，
说明这套 FLOPs 估算是可信的。而且原生 Wan2.2 还要跑 CFG，
每步要前向**两次**，实际还要再乘 2 —— MiniMax-H3 是 guidance-distilled 的，不用 CFG。）

三个结论：

1. **原生对原生，两者只差 4.8 倍**，基本就是参数量之比（33.12B / 5.00B = 6.6x）。
   Wan2.2 原生的 token 数（27,280）甚至比我们跑 MiniMax 时用的（8,370）还多 3 倍。
2. **真正把差距拉开的是 AHA-WAM 对 Wan2.2 的改造：整整 313 倍。**
   拆开是：token 27,280 → 480（**57x**）× 步数 50 → 20（**2.5x**）。
3. 所以"124 帧 vs 13 帧"这个对比**不是在比两个模型**，
   而是在比"生成一个 5 秒电影片段"和"预测机器人未来 3.2 秒"这两个**任务**。

### 2.4 AHA-WAM 到底改了什么、没改什么

先澄清一个常见误解：**"用 VAE 压缩后的画面"不是 AHA-WAM 的改动。**
所有 latent diffusion 视频模型都是这么干的——Wan2.1、Wan2.2、MiniMax-H3 全都是。
AHA-WAM 用的就是 Wan2.2 原装的那个 VAE（16 倍空间、4 倍时间、48 通道），一行没改。

真正改了的是：

| | 原生 Wan2.2-TI2V-5B | AHA-WAM 里的它 | 目的 |
| --- | --- | --- | --- |
| 分辨率 | 1280 x 704 | 384 x 320 | ↓ token（7.3x） |
| 帧数 / 帧率 | 121 帧 @ 24 fps（连续） | 13 帧 @ 3.75 fps（每 4 个控制帧取 1 帧） | ↓ token（7.75x） |
| 去噪步数 | 50（+ CFG 双倍前向） | 20（无 CFG） | ↓ 2.5x（含 CFG 则 5x） |
| 注意力掩码 | 双向（每帧看得到所有帧） | `per_frame_causal`（只能看过去） | 变成可流式的世界模型 |
| 历史 | 无 | 6 帧历史 K/V 前缀 | 记住更早的观察 |
| 额外分支 | 无 | ActionDiT + MoT + chunk KV editor | 出动作 |
| **VAE** | Wan2.2 VAE | **完全相同，没改** | — |

前三行是速度的来源（313 倍），后三行是"从视频生成器变成 world model"的来源。

### 2.5 那 MiniMax 照着改，能不能到同样的速度？

能改，而且改完差距只剩参数量那一项。把 MiniMax-H3 放到完全相同的工作点
（384x320、13 帧、480 token）：

| 配置 | FLOPs | 估算耗时 | 相对 AHA-WAM 现状 |
| --- | --- | --- | --- |
| AHA-WAM 现状（5B, 480 token, 20 步） | 74 TFLOP | 1.3 s | 1x |
| MiniMax 同工作点（33B, 480 token, 20 步） | 303 TFLOP | 5.4 s | **4.1x 慢** |
| MiniMax 同工作点 + 蒸馏到 4 步 | 60 TFLOP | 1.1 s | **0.8x（打平）** |
| MiniMax 同工作点 + 蒸馏到 1 步 | 15 TFLOP | 0.27 s | **0.2x（快 5 倍）** |

**所以答案是：能。**
把 token 砍到 480 之后，MiniMax 相对 AHA-WAM 就只剩 4.1 倍的劣势（纯粹是参数多），
再蒸馏到 4 步就能打平，蒸到 1 步比现在的 AHA-WAM 还快。

但"能"和"值得"是两回事，看 [第 3.4 节](#34-但还有两个现实障碍)：

- 33B 的权重就算蒸到 1 步也得常驻显存（int8 31.6 GiB / int4 19.5 GiB），
  A100-40GB 勉强够，机载算力没戏；
- 更要命的是，一旦把分辨率砍到 384x320、把连续 24 fps 换成每 4 个控制帧取 1 帧、
  再换成因果注意力，**MiniMax 原来那些优势（2K 画质、电影级运镜、音画同步）全都用不上了**，
  而它剩下的能力还得靠你的机器人数据重新训——那基本上就是把 AHA-WAM 重做一遍，
  只不过底座从 5B 换成 33B。

### 2.6 token 数为什么差 17 倍

参数量只差 6.6 倍，token 数却差 17.4 倍。而 token 数差在哪？

| | AHA-WAM | MiniMax-H3 | 倍数 |
| --- | --- | --- | --- |
| 画布 | 384 x 320 | 576 x 480 | 2.25x（面积） |
| 帧率 | 3.75 fps | 24 fps（**固定，不可调**） | 6.4x |
| 时长 | 3.2 s | 5.17 s（**最短就是 5 秒**） | 1.6x |
| 帧数 | 13 | 124 | 9.5x |
| latent 帧 | 4 | 31 | 7.75x |
| **token** | **480** | **8370** | **17.4x** |

**真正的元凶是"帧数"。**
AHA-WAM 只预测 13 帧（每 4 个控制帧取 1 帧，正好覆盖一个 3.2 秒的规划窗口），
而 MiniMax-H3 是个电影级视频模型，**硬性要求 24 fps、至少 5 秒**，
所以它被迫生成 124 帧——其中 90% 的帧对机器人控制毫无用处。

这不是我们没调好参数，是 MiniMax-H3 的架构约束
（帧数必须凑成 `17n+5`，时长必须落在 5～15 秒）。

### 2.7 注意力还有个平方项

注意力的计算量是 `O(token²)`，不是线性的：

- AHA-WAM：480 个 query 看 1200 个 key（480 当前 + 720 历史）→ 只占一层的 5.5%
- MiniMax-H3：8370 看 8370 → 占一层的 **28%**

所以 token 数一涨，注意力的占比也跟着涨，雪上加霜。

### 2.8 两边的实现效率其实是同一档

用 MFU（Model FLOPs Utilization，实际算力 / 硬件峰值）来看：

| | 理论下限（312 TFLOP/s 满载） | 实测 | MFU |
| --- | --- | --- | --- |
| AHA-WAM | 0.25 s | 1.2 s | 20% |
| MiniMax-H3 | 35.6 s | 232 s | 15% |

**两个都在 15～20%**，说明差距不是"哪个代码写得烂"，
而是实打实的计算量差了两个数量级。

### 2.9 结论

> **显存 ≈ 参数量 × 精度，计算量 ≈ 参数量 × token 数 × 步数。
> 量化只压了精度，所以显存追平了；但 MiniMax 的参数多 6.6 倍、token 多 17.4 倍、
> 步数多 1.6 倍，三者相乘就是两个数量级。
> 而 token 多 17 倍的根本原因，是它被迫按 24 fps 生成至少 5 秒（124 帧），
> 而机器人只需要 3.75 fps 的 13 帧。**

## 第 3 节：那 MiniMax 这类模型能不能嵌进 WAM？

分三层回答。

### 3.1 按现在这个跑法：绝对不行

你的在线 planner 每 `action_horizon = 40` 个控制帧刷新一次，
控制频率 15 Hz，所以预算是 **40 / 15 = 2.67 秒**。

| | 单次耗时 | 相对预算 |
| --- | --- | --- |
| 预算 | 2.67 s | 1x |
| AHA-WAM 视频分支 | 1.2 s | 0.45x ✅ |
| MiniMax-H3 int8 | 232 s | **87x** ❌ |
| MiniMax-H3 int4 | 988 s | **370x** ❌ |

而且要提醒一句（详见 [PATH_AUDIT_ZH.md](PATH_AUDIT_ZH.md) 第 6 节）：
**AHA-WAM 在线出动作时根本不生成未来视频**，只把当前帧编码进 K/V 缓存。
所以真实的在线预算比这里的 1.2 s 还要紧得多。

### 3.2 但"慢"是这个**跑法**的属性，不是这**类模型**的属性

上面 193 倍的差距，四个因子每一个都可以单独砍：

| 因子 | 现状 | 能砍到 | 收益 | 怎么砍 |
| --- | --- | --- | --- | --- |
| 去噪步数 | 31 | 1～4 | **8～31x** | 少步蒸馏 |
| token 数 | 8370 | 480 | **17x** | 短序列 + 低帧率 + 小画布 |
| 参数量 | 33.12 B | 5 B | **6.6x** | 换小模型 / 蒸馏 |
| 因果性 | 非因果，要等全部帧去噪完 | chunk-wise 因果 | 延迟摊薄 | 改注意力掩码 |

**这四件事恰好就是 Wan2.2 → AHA-WAM 走过的路。**
AHA-WAM 本质上就是"一个已经做完这些取舍的通用视频模型"：
它把 Wan2.2 的双向注意力换成 `per_frame_causal`、
把连续帧换成每 4 个控制帧取 1 帧、把长视频换成 13 帧的规划窗口。

而少步蒸馏这个仓库自己就有现成的：
`configs/model/ahawam_ode.yaml` 里 `default_action_inference_steps: 1`，
`src/ahawam/models/wan22/distill/` 下的 teacher/student 把一个 16 步的教师
蒸成 1 步的学生。学术界的
[Causal Forcing / Self Forcing](https://arxiv.org/abs/2602.02214) 系列
也是做到 2～4 步的实时交互式视频生成。

### 3.3 算一下：33B 搬到 AHA-WAM 的工作点会怎样

保持 MiniMax-H3 的 33B 参数不变，但把 token 数降到 480（3.2 秒、3.75 fps、384x320）、
再蒸馏到少步，按实测的 18% MFU 估算：

| 配置 | FLOPs | 估算耗时 | 放得进 2.67 s 预算吗 |
| --- | --- | --- | --- |
| 33B, 480 token, 31 步 | 469 TFLOP | 8.35 s | ❌ |
| 33B, 480 token, 8 步 | 121 TFLOP | 2.15 s | ✅ |
| 33B, 480 token, 4 步 | 60.5 TFLOP | 1.08 s | ✅ |
| 33B, 480 token, 1 步 | 15.1 TFLOP | **0.27 s** | ✅ 富余 10 倍 |

**所以答案是：能，但前提是同时做"缩短序列"和"少步蒸馏"两件事。**
只做量化（我们这次做的）完全解决不了问题——量化根本不动计算量。

### 3.4 但还有两个现实障碍

1. **显存**：33B 就算蒸到 1 步，权重还是得常驻。int8 是 31.6 GiB，int4 是 19.46 GiB。
   在 A100-40GB 上勉强可以，但如果将来想上机载算力（Jetson 之类）就完全没戏。
   5B 的 AHA-WAM 全部常驻才 17.29 GiB，而且里面还包含了动作分支和 VAE。
2. **蒸馏本身要重训**。而且 MiniMax-H3 是 guidance-distilled 的非因果模型，
   要改成因果注意力是一次结构性改动，[Causal Forcing 那篇](https://arxiv.org/abs/2602.02214)
   专门讨论了"把双向模型蒸成因果自回归模型"的架构鸿沟有多难跨。

### 3.5 结论

> **MiniMax-H3 这类模型不适合直接嵌进 WAM，但不是因为它"本质上不行"，
> 而是因为它现在的工作点（33B、8370 token、31 步、非因果）是为"生成 5 秒电影级视频"
> 优化的，和"2.67 秒内预测 3.2 秒机器人未来"完全不是一个需求。**

合理的定位：

| 用途 | 可行性 |
| --- | --- |
| 在线 world model | ❌ 差 87～370 倍 |
| **离线的视觉先验参照物**（本次实验做的） | ✅ 已经证明有用：零样本 13.11 dB，打平 AHA-WAM-Pretrained |
| **蒸馏教师 / 初始化权重** | 🤔 理论可行，但要做因果化改造 + 少步蒸馏 + 缩序列，工作量约等于重做一遍 AHA-WAM |
| 生成合成训练数据 | ✅ 慢一点无所谓，离线跑就行 |

**最有价值的一条**：本次实验已经量化地说明了，
MiniMax-H3 零样本的**画面先验**比 AHA-WAM-Pretrained 还好一点（13.11 vs 12.63 dB），
但它的**运动先验**是错的（帧间运动 13.60 vs 真值 6.65）。
而你的 SO101 微调 checkpoint 正好相反——画面和运动都对上了（15.89 dB，运动 7.40）。
这说明对机器人 world model 来说，**运动先验才是稀缺的那个**，
而它只能从机器人数据里学，不是靠堆一个更大的通用视频模型能白拿的。

## 第 4 节：所以到底值不值得改造 MiniMax？

### 4.1 先澄清：Wan2.2-TI2V-5B 不是蒸馏来的

它是**独立训练的 5B dense 模型**，不是从 A14B 蒸馏或裁剪出来的。
证据是两者的 VAE 都不一样：

| 模型 | 参数 | VAE | 压缩比 | latent 通道 |
| --- | --- | --- | --- | --- |
| Wan2.2-T2V/I2V-**A14B** | MoE，27B 总 / 14B 激活 | Wan2.1-VAE | 4 x 8 x 8 | 16 |
| Wan2.2-**TI2V-5B** | **5B dense** | **Wan2.2-VAE** | **4 x 16 x 16** | **48** |

latent 空间维度都不同，权重根本没法互相转换——
[官方 model card](https://huggingface.co/Wan-AI/Wan2.2-TI2V-5B) 把 TI2V-5B 描述为
"High-compression VAE, T2V+I2V, supports 720P" 的独立一档，
它的定位就是"能在消费级显卡上跑的那个版本"，为此专门配了个压缩率高 4 倍的 VAE
（加上 patchify 之后总压缩比 4x32x32）。

**这一点对你很关键**：AHA-WAM 选 TI2V-5B 不是因为"5B 是蒸馏出来的小模型所以将就用"，
而是因为它自带的高压缩 VAE 让同样画面的 token 数少 4 倍。
换句话说，**Wan 团队已经替你做了一半"降 token"的工作**。

### 4.2 更大的底座到底买到了什么（本次实测）

这是最有说服力的一组数字，全部来自同一批 16 个窗口：

| | PSNR | 帧间运动（真值 6.65） |
| --- | --- | --- |
| MiniMax-H3 **33B** 零样本 | 13.11 | 13.60 |
| AHA-WAM-Pretrained **5B** | 12.63 | 13.78 |
| 你的 SO101 微调 **5B** | **15.89** | **7.40** |

- **底座大 6.6 倍，只买到 +0.48 dB 的画面先验。**
- **运动先验一点没买到**：33B 的 13.60 和 5B 的 13.78 几乎一样，都是真值的 2 倍。
- **而用你自己的数据微调买到 +3.26 dB，并且把运动先验从 13.78 压到 7.40（接近真值 6.65）。**

**微调的收益是换底座的 6.8 倍。** 而且方向完全不同：
换底座只让画面更好看，微调才让"它接下来会怎么动"变对——
而后者才是 world model 真正要的东西。

### 4.3 代价

**训练显存**（全量微调，Adam：bf16 参数 2 + fp32 master 4 + m 4 + v 4 = 14 字节/参数）：

| 可训练参数 | 优化器+权重状态 | 4 x A100-40GB 放得下吗 |
| --- | --- | --- |
| 现在 7.28 B | 102 GB | ✅ ZeRO-3 分片后 25 GB/卡 |
| 换 33B 底座 35.40 B | **496 GB** | ❌ 124 GB/卡，必须把优化器和参数**全部** offload 到内存 |

这台机器 503 GB 内存还是和别人共用的，496 GB 的优化器状态基本没有余量。

**训练时间**：你这次 4 epoch / 4896 步实测跑了 **38.6 小时**。
换 33B 底座光 FLOPs 就是 6.6 倍 = **256 小时 ≈ 10.7 天**，
再叠加全量 CPU offload 的拖累，两三周起步。

**推理显存**：就算蒸馏到 1 步，33B 权重还是要常驻：int8 31.6 GiB / int4 19.5 GiB。
A100-40GB 勉强，机载算力（Jetson 之类）完全没戏。
而现在整个 AHA-WAM（含动作分支和 VAE）常驻才 17.29 GiB。

**工程量**：MiniMax-H3 是非因果 + guidance-distilled + 音视频联合打包序列。
要接进 AHA-WAM 得重写 `pre_dit`/`post_dit` 适配层、改因果掩码、接历史 K/V、
接 MoT 和 ActionDiT、再做少步蒸馏。而且它 33B 里有一部分是**音频分支**——
对机器人纯属死重量。

### 4.4 结论：不值得

> **换 6.6 倍大的底座，买到 0.48 dB 的画面先验和零运动先验改善，
> 代价是训练时间 x6.6（10 天起）、训练显存放不下、推理显存翻倍、
> 外加一次约等于重做 AHA-WAM 的移植工作。**

**唯一值得重新考虑的情况**：如果你的任务从现在的 4 个固定任务
变成开放世界（几十种物体、多变场景、需要视觉泛化），
那时"画面先验"才可能成为瓶颈，更大的底座才开始有意义。
现在不是。

### 4.5 同样的精力花在哪里 ROI 更高

按性价比排序：

| 优先级 | 做什么 | 依据 | 预期收益 |
| --- | --- | --- | --- |
| 1 | **加机器人数据** | 运动先验只能从机器人数据学，而它正是稀缺项（+3.26 dB vs +0.48 dB） | 直接命中瓶颈 |
| 2 | **少步蒸馏现有模型** | 仓库自带：`configs/model/ahawam_ode.yaml` + `src/ahawam/models/wan22/distill/`，20 步 → 1~4 步 | 在线快 5~20 倍，不需要新数据 |
| 3 | **设计更依赖上下文的任务** | 现在给不给 6 帧历史只差 0.07 dB（见 [README](README.md) "历史 K/V 的作用"），说明任务太短、首帧信息就够了，时序结构根本没被用上 | 让 world model 这个架构真正发挥作用 |
| 4 | 真想换更大底座 | 留在 Wan 家族用 A14B，AHA-WAM 代码基本能复用 | ⚠️ 但 A14B 用的是 Wan2.1-VAE（4x8x8），同分辨率下 token 数是 **4 倍**，比换 MiniMax 还贵 |

第 3 条尤其值得注意：你的微调模型对历史几乎不敏感（15.891 / 15.750 / 15.818，
三种历史设置差 0.07 dB），说明**现在这批数据根本没在训练"记忆"这个能力**。
在这个前提下堆更大的视频底座，等于给一辆没上路的车换发动机。

## 附：怎么复现这些数字

矩阵乘 microbenchmark 和 FLOPs 计算都是一次性脚本，逻辑很短，直接抄：

```python
# 1) GEMM microbenchmark：改 (M, K, N) 就能看到 memory-bound / compute-bound 的翻转
import torch, torch.nn as nn, time
from torchao.quantization import quantize_, Int8WeightOnlyConfig, Int4WeightOnlyConfig
from torchao.quantization.quantize_.workflows.int4.int4_packing_format import Int4PackingFormat

def bench(m, k, n, build, iters=30):
    lin = nn.Linear(k, n, bias=False).to("cuda", torch.bfloat16); build(lin)
    x = torch.randn(m, k, dtype=torch.bfloat16, device="cuda")
    for _ in range(5): lin(x)
    torch.cuda.synchronize(); t0 = time.perf_counter()
    for _ in range(iters): lin(x)
    torch.cuda.synchronize()
    ms = (time.perf_counter() - t0) / iters * 1000
    return ms, 2 * m * k * n / (ms / 1000) / 1e12   # ms, TFLOP/s

# 2) Transformer FLOPs
def flops(layers, hidden, ffn, attn_inner, tokens, kv, steps):
    lin = 2*tokens*hidden*3*attn_inner + 2*tokens*attn_inner*hidden + 4*tokens*hidden*ffn
    att = 4*tokens*kv*attn_inner
    return layers * (lin + att) * steps

flops(30, 3072, 14336, 24*128,  480, 1200, 20)   # AHA-WAM   ->    76.7 TFLOP
flops(50, 5376, 14336, 56*128, 8370, 8370, 31)   # MiniMax-H3 -> 11112.4 TFLOP
```

两个模型的几何参数来自：

- AHA-WAM：`runs/so101_g05_square_v1/full_zero3/<run>/model/config.yaml` 的 `video_dit_config`
- MiniMax-H3：`checkpoints/MiniMaxAI/MiniMax-H3/{transformer,vae}/config.json`
